# Evaluation Rubric, Three-Bucket Judge Protocol & Live Field-Test Calibration

This reference defines the evaluation methodology used by the **Frontier Judge & Architect Tier** to score blind code reviews, adjudicate novel findings, and calibrate skills from live field tests.

---

## 1. Asymmetric Grading Philosophy

Historical code reviews are **observational ground truth**, not exhaustive formal specifications:
1. **High Recall of Substantive Concerns Is Mandatory**: Every substantive bug, edge case, API design flaw, typing imprecision, or test gap that the human reviewer actually raised on the PR/changelist is a proven high-signal concern. The blind reviewer must catch these (**Target: 95–100% recall**).
2. **Extra Findings Require Value-Aligned Discrimination**: When a blind reviewer flags an issue that the human reviewer did *not* mention historically, it is **not** automatically a false positive. Human reviewers often stop after finding a blocking architectural flaw or miss a secondary bug in a 1,500-line diff. Conversely, uncalibrated LLMs frequently emit pedantic style noise that senior engineers actively dislike. Every unmatched finding must therefore be classified by the Frontier Judge into one of three buckets: `VALID_BONUS`, `NOISE_PENALTY`, or `AMBIGUOUS_QUEUE`.

---

## 2. Primary Metric: Recall of Substantive Ground-Truth Concerns

### Step 1: Filter the Ground-Truth Denominator
Before scoring recall on a record, the Frontier Judge classifies each item in `ground_truth_comments`:
- **Substantive Core Concern (Included in Denominator)**: Any comment identifying a correctness bug, edge case, API/signature design flaw, data-modeling/typing issue, backwards-compatibility hazard, unnecessary complexity, test coverage or mock-design flaw, error-handling issue, doc/description mismatch, or build/CI/VCS hygiene issue.
  - *Core Concern Clustering*: If the human made multiple identical inline comments pointing out the exact same pattern on 5 lines of the same file, the Judge may either score them individually (when testing line-by-line completeness) or group them into a Core Concern Cluster so a single repetitive PR does not skew corpus-wide macro averages. Report both cluster-level and comment-level recall when applicable.
- **Conversational / Context-Dependent Artifact (Excluded from Denominator)**: Purely social remarks (*"Thanks!"*, *"LGTM"*) or multi-turn replies that respond solely to a question or new code snippet proposed by the author *after* the initial diff.

### Step 2: Per-Concern Recall Scoring (`1.0`, `0.5`, `0.0`)

| Score | Label | Criteria |
| :---: | :--- | :--- |
| **`1.0`** | **Full Hit** | Identifies the same underlying technical issue, risk, or design question on the relevant code/file and captures the core reasoning or actionable fix. |
| **`0.5`** | **Partial Hit** | Flags the right code block or general symptom, or catches one half of a two-part concern (e.g., flags a helper as awkward but misses the specific exception-swallowing hazard). |
| **`0.0`** | **Miss** | Does not flag the issue or anything substantively related to it. |

- **Any-Hit Recall**: $\frac{\text{Count}(\text{score} \ge 0.5)}{N_{\text{sub}}}$
- **Weighted Recall**: $\frac{\sum_{i=1}^{N_{\text{sub}}} \text{score}(c_i)}{N_{\text{sub}}}$

## 3. Secondary Metric: Framing & Voice Alignment (`1–5` Scale)

The Frontier Judge grades each blind review on a `1.0` to `5.0` scale across four dimensions:
1. **Inquisitive & Collaborative Pragmatism**: Uses Socratic questions when intent or invariants are ambiguous (*"Should this be a `Sequence` or can it be a `Set`?"*, *"Do we have test coverage for both branches?"*) and distinguishes hard blockers from non-blocking inclinations (*"Nit: ..."*, *"Dealer's choice."*).
2. **Causal Rationale ("Explain the Why")**: Explains the concrete failure mode, runtime behavior, Hyrum's Law maintenance cost, or empirical micro-benchmark reason rather than reciting rigid style mandates.
3. **Concrete, Idiomatic Alternatives**: Supplies drop-in code snippets or `suggestion` fences.
4. **Temporal & Ecosystem Calibration**: Respects the PR/changelist's `review_date`, language version, and repository norms without anachronisms or cross-ecosystem rule leakage.

## 4. The Three-Bucket Protocol for Unmatched Extra Findings

Every comment generated by the blind reviewer that does not match a ground-truth comment is classified by the Frontier Judge into one of three buckets:

### Bucket A: Valid Unnoticed Catch (`VALID_BONUS`) — `0.0` Penalty
- **Criteria**: Identifies a genuine bug, subtle edge case, missing test branch, type imprecision, or maintainability hazard in the diff that is **100% consistent** with the engineer's documented philosophy and the PR's era/project context, such that the engineer would plausibly endorse it if pointed out.
- **Impact**: Zero penalty; tracked in `valid_bonus_count` as a positive quality signal.

### Bucket B: Irrelevant Noise / Anti-Pattern (`NOISE_PENALTY`) — `-0.25` Penalty
- **Criteria**: Factually wrong about the code, pedantic, anachronistic, or contrary to the engineer's review philosophy:
  1. **Library / Dependency Bikeshedding** (e.g., telling an author to replace `attrs` with `dataclasses` in an `attrs` codebase).
  2. **Formatter-Handled Style Nits** (line lengths, quote style, import sorting handled by automated formatters).
  3. **Anachronisms** (demanding syntax or stdlib modules that did not exist in the target language version).
  4. **Cross-Ecosystem Rule Leakage** (enforcing internal monorepo rules on external OSS repositories, or vice versa).
  5. **Vague Platitudes** (*"Make sure edge cases are tested"* without naming the exact untested line/branch).
  6. **Pro-Mock / Anti-Real-Test Advice** (asking to replace a fast real resource/temp-file test with `MagicMock`).
- **Impact**: **`-0.25` penalty** per `NOISE_PENALTY` comment against the composite score. Any noise item triggers a skill guardrail update during iterative refinement.

### Bucket C: Ambiguous Finding (`AMBIGUOUS_QUEUE`) — `0.0` Pending User Resolution
- **Criteria**: Technically plausible finding where competing principles in the engineer's corpus make it genuinely uncertain whether they would endorse it (`VALID_BONUS`) or consider it low-value churn (`NOISE_PENALTY`).
- **Protocol**: Append a structured entry (`AMB-001`, diff snippet, candidate comment, competing principles, and a concise multiple-choice question) to `ambiguous_for_user.md`. Follow the Phase 0 contract (either continue asynchronously with a best-effort call or block for user input). Once adjudicated by the user, fold the resolution permanently into both `eval_rubric.md` and the skill suite.

### Composite Score Formula
$$\text{CompositeScore} = \max\left(0.0,\; 0.80 \times \text{Recall}_{\text{PR}} + 0.20 \times \text{Voice}_{\text{norm}} - 0.25 \times N_{\text{noise}}\right)$$

## 5. Live Field-Test Postmortem Calibration Protocol (`v3 → v4+`)

Historical benchmark splits test recall on past reviews, but the ultimate test is deploying the skill on a **live PR or changelist** where the target engineer subsequently conducts their own review.

When the human engineer edits/deletes the agent's draft review comments or adds their own manual comments on a live change:
1. **Extract the Full Ground-Truth Delta**:
   - **Kept Agent Comments (`B_kept`)**: Validated hits that the human reviewer endorsed and published.
   - **Deleted / Modified Agent Comments (`B_deleted`)**: False positives, bikeshedding, or over-wordy comments rejected by the human.
   - **Newly Added Human Comments (`H_added`)**: Genuine concerns that the human added manually because the agent missed them.
2. **Root-Cause Every Miss (`H_added`) and Rejection (`B_deleted`)**:
   - Classify each miss into:
     - *Self-Capping / Multi-File Fatigue*: The skill had the rule, but the model stopped after finding 3–4 bugs in the file or bundled distant lines together.
     - *Missing Generalizable Pattern*: A recurring architectural, typing, or performance heuristic (e.g., config-driven tool modularity, `Set` vs `Sequence` semantics, union-of-products over product-of-unions, C-backed set intersection `bool(a & b)`, questioning `except ImportError:` fallback coverage) was not yet encoded in the domain sub-skills.
3. **Upgrade the Skill Without Overfitting**:
   - Add generalizable heuristics and voice patterns to the umbrella skill and domain sub-skills.
   - **Strict Anti-Overfitting Check**: Verify that **zero** variable names, class names, file paths, or changelist/PR IDs from the live change appear in `SKILL.md` or `references/*.md`.
4. **Blind Verification on Both Model Tiers**:
   - Reconstruct the pre-review blind prompt packet (`splits/blind_prompts/<live-id>.md`) from the exact snapshot the agent/human reviewed.
   - Run fresh blind evaluations with both the **Target / Fast Worker Tier** and the **Frontier Tier** and score against `H_added + B_kept` to verify `>= 90–100%` recall and `0` false positives.
